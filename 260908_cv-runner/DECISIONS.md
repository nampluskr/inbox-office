# DECISIONS

## D-1. model과 backbone의 선택 축

### 선택

model과 backbone을 서로 독립된 선택 항목으로 다룬다.

### 근거

사용자가 model과 backbone을 각각 선택하고, 같은 model에서 가능한 backbone을 바꾸어 실행할 수 있어야 한다. backbone을 사용하지 않는 model도 동일한 job 구조 안에서 표현할 수 있어야 한다.

### 배제한 대안

model과 backbone을 하나의 model 이름으로 합치는 방식을 배제한다. 이 방식은 model과 backbone의 독립적인 선택과 호환성 확인을 어렵게 한다.

## D-2. batch 행과 CLI 명령의 관계

### 선택

batch의 각 행은 하나의 독립된 CLI 명령에 대응한다.

### 근거

사용자가 표의 한 행을 하나의 실행 단위로 이해하고, 같은 작업을 batch 밖에서도 개별 CLI 명령으로 재실행할 수 있어야 한다.

### 배제한 대안

한 행에서 학습, 평가, 추론을 모두 묶어 암묵적으로 실행하는 방식을 배제한다. 이 방식은 행과 실제 실행 명령의 일대일 대응을 깨뜨리고 개별 작업의 재실행을 어렵게 한다.

## D-3. 초기 구현의 검증 대상

### 선택

실제 데이터셋과 model 대신 mock 구현을 사용하여 인터페이스, CLI와 batch 실행 형식을 먼저 검증한다.

### 근거

이번 작업의 목적은 개별 알고리즘 구현이 아니라, task나 model이 달라져도 유지되는 공통 실행 규격을 먼저 정하는 것이다.

### 배제한 대안

실제 데이터셋과 model을 먼저 통합한 뒤 공통 실행 규격을 추출하는 방식을 배제한다. 이전 프로젝트에서 이 순서로 인해 task와 model별 차이가 CLI와 batch 구조에 반복해서 반영되었다.

## D-4. batch job 실행 순서

### 선택

하나의 터미널에서 batch의 job을 정의된 순서대로 하나씩 실행한다.

### 근거

사용자가 batch의 행 순서와 실제 실행 순서를 동일하게 이해하고, 현재 실행 중인 job의 출력을 한 터미널에서 확인할 수 있어야 한다.

### 배제한 대안

여러 job을 동시에 실행하는 병렬 방식을 초기 실행 방식에서 배제한다. 병렬 실행은 batch 행의 순서와 실제 출력 순서를 다르게 만들 수 있다.

## D-5. job 실패 처리

### 선택

한 job이 실패하면 실패를 기록하고 다음 job으로 넘어간다.

### 근거

하나의 실패가 batch에 포함된 나머지 job의 실행을 막지 않아야 하며, 사용자는 batch 전체가 끝난 뒤 job별 결과를 확인할 수 있어야 한다.

### 배제한 대안

첫 job 실패 시 batch 전체를 즉시 중단하는 fail-fast 방식을 배제한다. 이 방식은 서로 독립된 뒤의 job을 실행하지 못하게 한다.

## D-6. job별 logging

### 선택

학습, 평가, 추론을 포함한 각 job은 `logging` 기반으로 독립된 로그를 기록한다.

### 근거

터미널 출력과 별개로 각 job의 시작, 진행, 완료 또는 실패 내용을 해당 job 단위로 다시 확인할 수 있어야 한다.

### 배제한 대안

터미널 출력만 남기거나 여러 job이 하나의 로그 파일을 공유하는 방식을 배제한다. 이 방식은 특정 job의 실행 기록과 실패 원인을 구분하기 어렵게 한다.

## D-7. batch 기록 형식

### 선택

전체 batch 정의, 실행할 job 목록과 각 job의 진행 상태를 하나의 JSON 파일에 기록한다. job의 결과물과 전체 로그를 JSON에 포함하지 않고, 해당 결과 폴더와 로그 파일의 경로를 기록한다.

### 근거

실행 전에 batch 전체 구성과 job 순서를 저장하고, 실행 중에는 같은 파일에서 현재 진행 상태를 확인할 수 있어야 한다. 결과물과 로그는 job별 결과 폴더에 두어 JSON이 실행 상태를 확인하는 색인 역할을 하게 한다.

### 배제한 대안

batch 구성을 Python 코드의 목록이나 주석으로 관리하는 방식과 진행 상태를 별도의 result JSON으로 분리하는 방식을 배제한다. Python 코드 방식은 실행 구성을 코드 변경과 분리하기 어렵고, 별도 result JSON 방식은 현재 상태를 확인하기 위해 두 파일을 함께 추적해야 한다.

## D-8. job 결과 격리

### 선택

각 job은 독립된 결과 폴더에 자신의 결과물과 로그를 기록한다.

### 근거

여러 job이 순차 실행되더라도 각 job의 입력, 실행 기록과 결과를 다른 job과 섞이지 않게 확인할 수 있어야 한다.

### 배제한 대안

모든 job이 하나의 결과 폴더와 로그 파일을 공유하는 방식을 배제한다. 이 방식은 결과의 소유 job과 실패 원인을 구분하기 어렵게 한다.

## D-9. batch terminal 수명

### 선택

batch는 사용자가 볼 수 있는 터미널에서 실행하며, 모든 job이 끝난 뒤에도 terminal을 자동으로 닫지 않는다. 사용자가 진행 상태와 최종 완료 상태를 확인한 후 terminal을 직접 닫는다.

### 근거

사용자는 별도 화면 없이 terminal을 통해 현재 진행 상태와 전체 batch의 종료 여부를 확인할 수 있어야 한다.

### 배제한 대안

마지막 job이 끝나는 즉시 terminal을 자동으로 닫는 방식을 배제한다. 이 방식은 사용자가 마지막 출력과 전체 완료 상태를 확인하기 어렵게 한다.

## D-10. batch JSON 관리 CLI

### 선택

`cv-batch-runner`는 `backlog`의 JSON 관리 방식만 참고하여 CLI 중심으로 batch JSON을 관리한다. JSON을 실행 상태의 SSOT로 두고, CLI가 문서 검증, job 목록과 상세 조회, 안전한 상태 변경과 batch 실행을 담당한다. `backlog`를 호출하는 AI agent의 역할은 차용하지 않는다. 정확한 subcommand와 option은 이후 interface 규격에서 확정한다.

### 근거

`backlog`는 `--file`로 JSON을 선택하고 subcommand로 검증, 조회와 변경을 수행한다. 쓰기 전후 전체 문서를 검증하고 임시 파일 작성 후 원본을 교체하여 JSON 손상을 방지한다. 같은 방식을 사용하면 UI와 terminal runner가 공유하는 batch 상태를 일관된 규칙으로 관리할 수 있다.

### 배제한 대안

UI, batch runner와 개별 script가 각자 다른 방식으로 JSON을 직접 수정하는 방식을 배제한다. 쓰기 규칙이 여러 곳에 분산되면 검증과 상태 전이 규칙이 달라지고 실행 중 JSON이 손상될 수 있다.

## D-11. AI agent 비의존 실행

### 선택

AI agent를 batch runtime에 포함하지 않는다. 사용자 또는 UI가 실행을 시작하면 runner가 JSON에 정의된 순서와 CLI process의 종료 결과만으로 job을 순차 실행하고 상태를 변경한다.

### 근거

같은 batch JSON은 AI의 판단, 응답 가능 여부나 모델 변경과 관계없이 항상 같은 실행 순서와 상태 전이 규칙을 따라야 한다. 사용자는 terminal과 dashboard에서 프로그램이 기록한 상태를 직접 확인할 수 있어야 한다.

### 배제한 대안

AI agent가 다음 job을 선택하거나, CLI를 대신 호출하거나, 로그를 해석해 완료와 실패를 판단하는 방식을 배제한다. 이 방식은 실행 결과를 AI의 판단과 가용성에 의존하게 한다.
