## `Editor Group`의 기본 `Untitled` 상태

### UT-EDT-004 — 첫 번째 칸과 분할 칸의 `Untitled` `Preview Tab` 규칙 통일

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | `Split Right` 또는 `Split Down`을 실행해 새 `Editor Group`을 만들면 이탤릭 제목의 `Untitled` `Preview Tab`이 기본으로 생긴다. 반면 첫 번째 `Editor Group`에서 `[+]`로 만든 `Untitled`는 이탤릭이 아닌 `Pinned Tab`으로 생성된다. |
| 현재 판정 | 같은 `Untitled` 빈 탭이 생성 위치에 따라 서로 다른 수명 규칙을 사용한다. 첫 번째 칸과 다른 분할 칸의 탭 동작이 일관되지 않는다. |
| 원인 분석 | 첫 번째 칸의 `[+]` 경로는 `Untitled`를 `isPreview: false`로 만들고, 사용자 스플릿 경로는 `isPreview: true`로 만든다. 따라서 전자는 처음부터 `Pinned Tab`, 후자는 교체 가능한 `Preview Tab`으로 표시된다. 이 차이는 두 호스트가 공유하는 에디터 코어에서 발생하므로 Electron과 pywebview에서 동일하다. |
| 사용자 요청 | 첫 번째 `Editor Group`과 `Split Right`·`Split Down`으로 만든 다른 `Editor Group`에서 탭 생성 및 교체 동작이 같아야 한다. 칸이 처음부터 있던 칸인지 나중에 분할된 칸인지는 `Preview Tab`과 `Pinned Tab`을 결정하는 조건이 되어서는 안 된다. |
| 핵심 원칙 | 동일한 사용자 조작은 어느 `Editor Group`에서 실행해도 동일한 탭 상태와 결과를 만든다. 첫 번째 칸과 다른 분할 칸 사이에 예외를 두지 않는다. |
| 기대 결과 | 첫 번째 칸과 `Split Right`·`Split Down`으로 만든 칸에서 생성되는 기본 `Untitled`가 모두 이탤릭 제목의 `Preview Tab`으로 표시된다. 어느 칸에서든 파일이나 폴더를 한 번 선택하면 그 칸의 `Untitled` `Preview Tab`이 선택한 대상으로 교체되며, 불필요한 `Untitled` `Pinned Tab`이 남지 않는다. 같은 `[+]` 조작과 같은 항목 선택 조작은 모든 칸에서 동일하게 동작한다. |
| 호스트 공통 조건 | Electron과 pywebview에서 생성 경로, 이탤릭 표시, 선택 항목으로의 교체 결과가 같아야 한다. |
| 재검증 기준 | 두 호스트를 각각 새로 실행한다. 첫 번째 칸과 `Split Right`·`Split Down`으로 만든 칸에서 `[+]`, 파일 한 번 선택, 폴더 한 번 선택을 같은 순서로 실행한다. 각 단계의 탭 수, 활성 탭, `Untitled` 제목의 이탤릭 여부, 선택 대상으로의 교체 여부가 모든 칸에서 같아야 한다. 어느 칸에서도 생성 위치 때문에 `Pinned Tab`으로 달라지거나 빈 `Untitled` `Pinned Tab`이 남아서는 안 된다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |

### UT-EDT-005 — 모든 칸의 `[+]` 새 탭을 `Preview Tab`으로 생성

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | 첫 번째 칸과 `Split Right`·`Split Down`으로 만든 다른 모든 칸에서 `[+]`를 누르면 `Untitled`가 이탤릭이 아닌 `Pinned Tab`으로 생성된다. |
| 현재 판정 | 모든 칸의 `[+]` 새 탭이 `Pinned Tab`으로 생성되므로 요청한 기본 `Preview Tab` 동작과 다르다. |
| 원인 분석 | 모든 칸의 `[+]` 버튼은 공통 `addNewTab()` 경로를 사용하며, 이 경로가 `Untitled`에 `isPreview: false`를 지정한다. 따라서 첫 번째 칸과 모든 분할 칸에서 `[+]`로 만든 탭이 동일하게 `Pinned Tab`이 된다. 이 차이는 두 호스트가 공유하는 에디터 코어에서 발생하므로 Electron과 pywebview에서 동일하다. |
| 사용자 요청 | 첫 번째 칸과 모든 분할 칸에서 `[+]` 새 탭을 클릭하면 `Untitled`가 `Pinned Tab`이 아니라 `Preview Tab`으로 생성되어야 한다. |
| 기대 결과 | 어느 칸에서든 `[+]`를 누르면 이탤릭 제목의 `Untitled` `Preview Tab`이 생성된다. 이어서 파일이나 폴더를 한 번 선택하면 `[+]`로 만든 그 칸의 `Untitled` `Preview Tab`이 선택한 대상으로 교체되며, 빈 `Untitled` `Pinned Tab`이 남지 않는다. |
| 호스트 공통 조건 | Electron과 pywebview에서 `[+]` 생성 결과, 이탤릭 표시, 선택 항목으로의 교체 결과가 같아야 한다. |
| 재검증 기준 | 두 호스트를 각각 새로 실행한다. 첫 번째 칸, `Split Right`로 만든 칸, `Split Down`으로 만든 칸에서 각각 `[+]`를 클릭한다. 세 칸 모두 새 `Untitled`가 이탤릭 `Preview Tab`인지 확인한다. 각 칸에서 파일 또는 폴더를 한 번 선택한 뒤 `[+]`로 만든 동일한 탭이 해당 대상으로 교체되고, 빈 `Untitled` `Pinned Tab`이 남지 않는지 확인한다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |

## `Explorer`의 새 파일·새 폴더 생성

### UT-EXP-007 — 이름 입력 완료 시 실제 파일·폴더 생성

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | 탐색기 트리에서 `New File` 또는 `New Folder`를 누르면 새 이름을 입력할 수 있고 `Enter`로 입력을 완료할 수 있다. 그러나 입력한 이름의 실제 파일 또는 폴더는 디스크에 생성되지 않는다. |
| 현재 판정 | 인라인 이름 입력 UI까지만 동작하며, 사용자가 요청한 파일시스템 변경까지 완료되지 않는다. |
| 원인 분석 | 이름 입력을 완료하면 공통 껍데기가 앱의 새 항목 콜백을 호출한다. 현재 연결된 예제 앱 핸들러는 실제 생성 대신 `App would create ...` 상태 메시지를 표시하고 트리를 새로고침한다. Electron과 pywebview의 호스트 브리지에도 디렉터리 읽기 기능만 있고 파일 또는 폴더를 생성하는 기능은 연결돼 있지 않다. |
| 사용자 요청 | `New File`과 `New Folder`에서 이름 입력을 완료하면 현재 탐색기 위치에 입력한 이름의 실제 파일 또는 폴더가 생성되어야 한다. |
| 기대 결과 | `New File`에서 이름을 입력하고 `Enter`를 누르면 해당 경로에 실제 파일이 존재하고, `New Folder`에서 이름을 입력하고 `Enter`를 누르면 해당 경로에 실제 폴더가 존재한다. 생성 직후 탐색기 트리를 갱신했을 때 새 항목이 표시되어야 한다. |
| 취소 조건 | 이름 입력 중 `Escape`를 누르면 입력 행만 닫히고 실제 파일과 폴더는 생성되지 않는다. |
| 호스트 공통 조건 | Electron과 pywebview에서 같은 이름과 같은 탐색기 위치를 사용했을 때 실제 생성 여부와 트리 갱신 결과가 같아야 한다. |
| 재검증 기준 | 두 호스트에서 쓰기 가능한 임시 폴더를 탐색기 루트로 연다. 루트와 하위 폴더에서 각각 `New File`과 `New Folder`를 실행하고 서로 다른 이름을 입력한 뒤 `Enter`를 누른다. 디스크에서 각 경로가 올바른 파일·폴더 유형으로 존재하는지 확인하고, 탐색기 트리에도 새 항목이 표시되는지 확인한다. 별도의 이름으로 입력을 시작한 뒤 `Escape`를 눌러 해당 경로가 생성되지 않는지도 확인한다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |

## `Explorer` 트리 계층 정렬

### UT-EXP-008 — 세로 정렬선·아이콘·이름 간격을 VS Code와 일치

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | 탐색기 트리에서 폴더를 펼치면 나타나는 계층 세로 정렬선이 왼쪽으로 치우쳐 보인다. 세로선과 폴더·파일 아이콘, 항목 이름 사이의 가로 간격도 VS Code와 다르다. |
| 현재 구현 점검 | 하위 단계마다 14px 들여쓰기 단위를 하나씩 추가하고, 세로 정렬선을 각 단위의 왼쪽 끝인 `left: 0`에 그린다. 이어서 18px `Twistie`, 18px 폴더·파일 아이콘, 아이콘 오른쪽 5px 여백, 항목 이름 순서로 배치한다. 이 구조 때문에 세로선이 해당 계층의 시각적 중심보다 왼쪽에 놓인다. |
| 현재 판정 | 세로 정렬선의 x좌표와 세로선 이후 `Twistie`·아이콘·이름으로 이어지는 가로 간격이 VS Code 탐색기 트리와 일치하지 않는다. |
| 사용자 요청 | 계층 세로 정렬선을 현재 위치보다 오른쪽으로 옮기고, 세로 정렬선·`Twistie`·폴더 및 파일 아이콘·항목 이름 사이의 가로 위치와 간격을 VS Code 탐색기 트리와 일치시킨다. |
| 기대 결과 | 폴더를 펼쳤을 때 각 계층의 세로 정렬선이 VS Code와 같은 x좌표에 표시된다. 각 깊이에서 세로선부터 `Twistie`, 아이콘, 항목 이름까지 이어지는 상대 위치와 간격이 VS Code와 같고, 폴더 행과 파일 행 및 열린·닫힌 폴더 상태에서 정렬이 흔들리지 않는다. |
| 적용 범위 | 루트 바로 아래부터 두 단계 이상 중첩된 모든 계층의 폴더·파일 행, 열린 폴더와 닫힌 폴더, `Twistie`가 있는 행과 없는 행, 두 `File Icon Theme`에 동일한 정렬 규칙을 적용한다. |
| 호스트 공통 조건 | Electron과 pywebview에서 깊이별 세로선 x좌표와 `Twistie`·아이콘·이름의 가로 간격이 같아야 한다. |
| 재검증 기준 | 두 단계 이상 중첩된 동일한 폴더 구조를 workbench-kit과 VS Code에서 각각 연다. 같은 깊이의 폴더 행과 파일 행에서 세로 정렬선, `Twistie`, 아이콘, 항목 이름의 시작 x좌표를 측정하고 인접 요소 사이 거리를 대조한다. 폴더를 펼치고 접은 뒤에도 각 위치가 VS Code 기준과 일치하는지 확인하며, `VS Code Built-in`과 `VS Code Icons` 두 테마 및 두 호스트에서 반복한다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |

## 탐색기와 에디터의 선택 표시

### UT-FCS-004 — 선택 배경과 `Focus Ring`을 두 영역에서 통일

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | 탐색기 트리의 선택된 항목은 직사각형 내부가 파란색으로 표시된다. 이 표시는 에디터 칸의 선택 표시와 색과 테두리가 달라, 탐색기와 에디터 칸 사이를 번갈아 이동할 때 서로 다른 선택 체계처럼 보인다. |
| 현재 구현 점검 | 탐색기 선택 행은 파란 계열의 메뉴 선택 배경과 흰색 전경을 사용한다. 탐색기에 포커스가 있을 때는 선택 행 안쪽에 1px 테두리를 추가한다. 에디터의 활성 탭은 에디터 내부 배경과 같은 계열의 활성 탭 배경을 사용하고, 현재 포커스가 있는 칸의 활성 탭에 별도의 1px 테두리를 표시한다. |
| 현재 판정 | 탐색기 선택 행과 에디터 칸의 활성 선택 표시가 서로 다른 배경색과 테두리색을 사용하므로 요청한 공통 시각 규칙과 다르다. |
| 사용자 요청 | 탐색기에서 선택된 항목의 직사각형 내부를 에디터 영역의 내부색과 같게 한다. 탐색기와 에디터 칸 사이에서 포커스를 번갈아 이동할 때 선택된 대상이 같은 배경색과 같은 테두리로 표시되도록 통일한다. |
| 기대 결과 | 탐색기 선택 행과 에디터 칸의 활성 선택 표시는 동일한 계산 배경색을 사용한다. 현재 포커스가 있는 영역의 선택 대상에는 두 영역에서 동일한 색·두께·안쪽 배치의 `Focus Ring`이 나타난다. 포커스가 다른 영역으로 이동하면 기존 선택 상태는 유지되고 `Focus Ring`만 현재 영역으로 이동한다. |
| 상태 구분 | 선택 표시와 hover 표시는 서로 구분되어야 한다. 탐색기 항목 선택, 에디터 활성 탭, `Preview Tab`의 이탤릭, `Pinned Tab`의 일반 글꼴 상태는 공통 배경과 테두리를 적용한 뒤에도 각각 판별할 수 있어야 한다. |
| 테마·호스트 공통 조건 | 모든 `Color Theme`에서 탐색기와 에디터의 선택 배경 및 `Focus Ring` 계산 색이 서로 같아야 하며, Electron과 pywebview에서도 같은 결과가 나와야 한다. 테마마다 사용할 실제 색은 달라질 수 있지만 한 테마 안에서는 두 영역이 반드시 같은 색과 같은 테두리 규칙을 사용한다. |
| 테마 전환 조건 | 앱을 다시 열지 않고 `White`·`Gray`·`Dark` 사이를 전환해도 선택 배경과 `Focus Ring`이 현재 테마의 색으로 즉시 함께 갱신되어야 한다. 전환 직후에도 탐색기와 에디터 중 한쪽만 이전 테마 색을 유지하거나 서로 다른 테마 토큰을 사용해서는 안 된다. |
| 재검증 기준 | 두 호스트의 모든 `Color Theme`에서 탐색기 항목 하나와 둘 이상의 에디터 칸에 각각 활성 탭을 둔다. 탐색기와 각 칸으로 포커스를 차례로 이동하면서 선택 행과 활성 탭의 계산 배경색, 테두리색, 테두리 두께와 안쪽 배치를 측정한다. 이어서 선택 상태를 유지한 채 `White`→`Gray`→`Dark`와 역순으로 테마를 전환하고, 매 전환 직후 두 영역의 색과 테두리가 같은 테마 값으로 함께 바뀌는지 확인한다. `Focus Ring`만 현재 포커스 영역으로 이동하고 기존 선택 상태와 hover·Preview·Pinned 구분이 유지되어야 한다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |

## `Activity Bar` 아이콘 간격

### UT-ACT-002 — 아이콘 액션 영역의 세로 간격 축소

| 구분 | 내용 |
| --- | --- |
| 사용자 확인 | `Activity Bar`의 각 아이콘 영역 높이가 크게 잡혀 있어 위아래 아이콘 사이 간격이 넓게 보인다. |
| 비교 기준 | 탐색기 헤더 우측의 `New File`·`New Folder`·`Refresh`·`Collapse All` 아이콘과 탭 영역 우측의 `Split Right`·`Split Down`·`New Tab` 아이콘은 작은 액션 영역과 좁은 간격으로 연속 배치되어 있다. `Activity Bar`도 이들 액션 영역과 같은 수준의 조밀한 간격을 사용한다. |
| 현재 구현 점검 | `Activity Bar`의 너비는 30px이지만 각 아이콘 버튼 높이는 50px이고 아이콘 크기는 20px이다. 비교 대상인 탐색기 헤더와 탭 영역의 버튼은 22px × 22px이며 버튼 사이 간격은 2~3px이다. 큰 50px 버튼 높이가 `Activity Bar` 아이콘 사이의 넓은 세로 간격을 만든다. |
| 현재 판정 | `Activity Bar` 아이콘의 세로 액션 영역과 간격이 비교 대상보다 커서 요청한 조밀도와 다르다. |
| 사용자 요청 | `Activity Bar` 아이콘 영역의 높이와 아이콘 사이 세로 간격을 줄여, 탐색기 헤더 우측 아이콘 또는 탭 영역 우측의 스플릿·추가 아이콘 영역처럼 조밀하게 배치한다. |
| 기대 결과 | `Activity Bar`의 연속된 아이콘 버튼이 탐색기 헤더 및 탭 우측 액션과 같은 수준의 작은 액션 영역과 좁은 간격으로 표시된다. 상단 그룹과 하단 그룹의 정렬 구조는 유지하고, 각 그룹 안의 아이콘 사이에 현재와 같은 큰 빈 세로 영역이 남지 않는다. |
| 호스트 공통 조건 | Electron과 pywebview에서 `Activity Bar` 아이콘 영역의 높이, 아이콘 사이 간격, 상단·하단 정렬 결과가 같아야 한다. |
| 재검증 기준 | 두 호스트에서 `Activity Bar` 상단과 하단의 연속된 아이콘 버튼 높이와 버튼 사이 세로 거리를 측정한다. 같은 화면의 탐색기 헤더 우측 액션과 탭 우측 액션의 22px 버튼 및 2~3px 간격과 대조해 같은 수준으로 조밀한지 확인한다. hover·active 배경도 축소된 액션 영역에 맞게 표시되고, 각 아이콘을 클릭할 수 있는지 확인한다. |
| 재검증 결과 | 미실시. 코드 수정 후 확인한다. |
