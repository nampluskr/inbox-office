# DECISIONS — workbench-kit

## D-1. 무빌드 원칙을 폐기하고 빌드를 전제로 한다

**선택**

이전 프로젝트(`tab-explorer-templates` · `markdown-viewer`)가 지켰던 "번들러 없이
그대로 로드하는 무빌드" 원칙을 이번 프로젝트에서는 따르지 않는다. 빌드 단계를 두고,
코드가 바뀌면 무조건 재빌드하는 것을 기본으로 한다.

**근거**

이 프로젝트의 원칙은 "무빌드"가 아니라 **"최소 구현"**이다. 필요한 기능을 제대로
구현하고 빌드해서 쓰는 편이, 무빌드 제약에 맞추느라 기능을 우회하거나 좁히는 것보다
목적에 맞다. 빌드를 전제해야 monaco-editor · codicons 같은 빌드형 라이브러리를 쓸 수
있다(D-2). 이것이 이전 프로젝트에서 이번 프로젝트로 넘어오며 바뀐 지점이다.

**배제한 대안**

- **무빌드 원칙을 유지한다(이전 프로젝트 방식).** 번들러 없이 로드되는 배포본만 써야
  해서 쓸 수 있는 라이브러리와 구현 방식이 좁아진다. 최소 구현을 오히려 방해하므로
  배제한다.

## D-2. VS Code OSS는 fork하지 않고 참고만 하며, bottom-up으로 필요한 기능만 구현한다

**선택**

VS Code OSS 저장소를 fork해 불필요한 것을 걷어내는 방식(top-down)을 쓰지 않는다.
VS Code OSS는 동작과 구현을 참고하는 자료로만 보고, 이 프로젝트에 필요한 기능만
밑에서부터 새로 구현한다(bottom-up). 다만 monaco-editor · codicons처럼 독립적으로
배포되어 빌드해 쓸 수 있는 라이브러리는 그대로 가져다 쓴다.

**근거**

제1원칙이 최소 구현이다. VS Code 전체를 안고 축소하면 쓰지 않는 방대한 코드와 그
상태·예외를 계속 떠안게 되어 최소·단순과 정반대가 된다. 필요한 기능만 참고해 새로
짜면 껍데기가 작게 유지되고, 왜 그 동작이어야 하는지를 VS Code라는 외부 기준과
대조할 수 있다(BRIEF의 기준 문서). 반대로 이미 검증된 라이브러리를 다시 만드는 것도
최소 구현에 어긋나므로, 그런 것은 반입한다.

**배제한 대안**

- **VS Code OSS를 fork해 축소한다(top-down).** 방대한 미사용 코드와 그 유지 부담을
  그대로 안게 되어 최소 구현 원칙과 어긋나므로 배제한다.
- **라이브러리도 쓰지 않고 전부 자체 구현한다.** monaco-editor · codicons처럼 이미 잘
  만들어진 것을 다시 만드는 비용이 크고, 이 역시 최소 구현에 어긋나므로 배제한다.
