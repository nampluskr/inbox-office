# DOCUMENTS — 문서 작성 기준

## 공통 원칙

- 루트 `INTENT.md`는 프로젝트 전체의 목적과 판단 기준이다.
- `specs/{version}/INTENT.md`는 이번 버전의 목적과 범위다.
- 설계 문서 네 개는 모두 첫 항목으로 `INTENT`를 둔다. 그 안에 단계의 목적·범위·기대 결과를 적는다.
- `PROGRESS.md`는 에이전트가 실제 수행 내용을 기록하는 실행 문서이며 별도의 설계 단계가 아니다.
- INTENT 문서 자체가 첫 단계의 의도를 담으므로 중복된 의도 파일은 만들지 않는다.
- 하위 단계는 상위 의도를 구체화한다. 상위 내용을 복사하지 않고 해당 단계의 의도만 적는다.
- 사용자는 요구와 결정을 정한다. 에이전트는 요청받은 초안을 작성하고 모호한 점을 질문한다.
- 작성 중 미결 사항은 `미정`으로 표시한다. 미정인 내용에 의존하는 구현은 방향이 정해진 뒤 진행한다.
- 해당 사항이 없으면 `없음`으로 적는다. 문서 분량과 결정 개수를 채우기 위한 내용을 만들지 않는다.
- Markdown은 UTF-8로 저장하고 다시 읽어 한글 손상을 확인한다. 이모지는 사용하지 않는다.

버전은 폴더명으로 식별한다. 문서마다 같은 버전 정보를 반복 입력하도록 강제하지 않는다.

## 문서별 최소 항목

| 문서 | 항목 | 담는 내용 |
| --- | --- | --- |
| INTENT | INTENT | 이번 버전의 목적·범위·기대 결과 |
| INTENT | 배경 / 제외 범위 | 해결할 문제와 이번에 다루지 않을 것 |
| DECISIONS | INTENT | 이번 단계에서 선택·확정할 대상과 기대 결과 |
| DECISIONS | 결정 사항 / 미결 사항 | 선택, 근거, 검토한 대안과 남은 판단 |
| SPEC | INTENT | 명세할 대상과 범위, 판정 가능한 결과 |
| SPEC | 요구사항 / 제약 | 요구별 식별자, 내용, 완료 판정 방법, 적용 제약 |
| PLAN | INTENT | 실행 계획의 목적·범위·기대 결과 |
| PLAN | Phase별 작업 / 에이전트 구성 | 목적·순서·담당·완료 기준과 검증 계획 |
| PROGRESS | Phase별 진행사항 / 작업 기록 | PLAN의 Phase·작업별 현재 상태, 일자·수행 내용·검증 결과·남은 문제 |
| PROGRESS | 사용자 요청 작업 내역 | 요청 내용·조치·결과·검증·상태와 관련 Phase·작업 |
| PROGRESS | 버전 종료 | 사용자 종료 판단과 남은 사항 |

SPEC의 요구는 버전 안에서 구별할 수 있는 `R-1`, `R-2` 등의 식별자를 사용한다.
PLAN은 `Phase 1`, `Phase 2` 등으로 작업을 묶고, 각 Phase의 목적과 완료 기준을 적는다.
PLAN 작업은 대응 요구를 참조하고 검증 가능한 완료 기준을 갖는다.
PROGRESS는 같은 Phase·작업 번호로 실제 진행과 검증 결과를 연결한다.
Phase 착수·상태 변경·작업 완료·문제 발생 시 기록하고, 사용자 요청에 대한 작업 내역도 남긴다.
현재 상태 요약은 갱신하되 기존 작업 기록과 요청 이력은 삭제하거나 덮어쓰지 않는다.
DECISIONS는 선택이 필요했던 사항을 기록한다. 결정이 없으면 `없음`으로 유지할 수 있다.

## 의도와 문서 정합성

프로젝트 INTENT → 버전 INTENT → 단계별 INTENT와 결과물의 관계로 확인한다.
어긋남을 발견하면 사용자에게 충돌을 설명한다. 에이전트가 상위 의도를 임의로 바꾸지 않는다.
사용자가 방향을 정하면 영향을 받는 문서와 작업을 함께 갱신한다.

검토 시 문서 개수나 분량보다 다음을 확인한다.

- 목적과 제외 범위를 이해할 수 있는가.
- 결정과 요구가 의도에 부합하는가.
- 각 요구의 충족 여부를 판정할 수 있는가.
- 계획이 요구를 빠뜨리지 않고 담당·순서·검증 방법을 정했는가.
- 진행 상태와 검증 결과가 실제 수행 내용과 일치하는가.
