# 실습 노트북 문서 작성 및 수정 요령

## 가이드의 목적과 적용 범위

현재 세션에서 사용자가 요청한 실습 문서 작성 방식과 후속 수정사항을 정리합니다. Jupyter Notebook에 옮겨 실습할 수 있는 Markdown 문서를 작성하거나 수정할 때 적용합니다.

교육 내용은 [COURSE.md](../COURSE.md)를 기준으로 하고, 문서 형식은 [LLM API와 메시지 역할 실습](02-llm-api-and-message-roles.md)을 현재 적용 사례로 참조합니다. 문서 작성의 공통 기준은 `D:\projects\_clones\project-workflow\WORKFLOW.md`와 `docs\DOC-SCHEMA.md`를 원래 위치에서 확인합니다.

## 1. 사용자 요청과 최종 적용 기준

| 구분 | 사용자 요청 | 최종 적용 기준 |
| --- | --- | --- |
| 최초 구성 | 일차별 교육용 노트북의 폴더명과 파일명만 제시 | 요청 당시에는 목록만 제시하고 노트북 파일을 생성하지 않음 |
| 목록 보관 | 비교 분석 문서 마지막에 노트북 목록 포함 | [TECH-STACK-COMPARISON.md](../TECH-STACK-COMPARISON.md)의 구성안을 참조 |

| 코드 앞 설명 | 실습 목적과 내용 포함 | 목적과 내용을 항목별 불릿으로 설명 |
| 코드 뒤 설명 | 결과 설명 포함 | 코드 뒤에 예상 출력과 해석을 항목별 불릿으로 설명 |
| 설명 형식 수정 | 목적·내용과 결과 설명을 불릿으로 구분 | 긴 설명 문단을 의미별 불릿으로 분리 |

| 결과 표시 변경 | ‘결과 설명:’을 ‘결과:’로 변경 | 코드 뒤에 `**결과:**`와 불릿 배치 |
| 제목 체계 | `N. 섹션 제목`과 `N.N 서브섹션 제목` 사용 | 실습을 주제별 섹션으로 묶고 각 셀 제목을 하위 번호로 표시 |
| 문서 저장 | 이모지 금지, UTF-8, 한글 확인 | 저장 후 인코딩과 한글 보존 확인 |

후속 수정 요청이 이전 형식을 구체화한 경우에는 최종 요청을 적용합니다. 예를 들어 최초 요청의 목적·내용 자체는 유지하되, 그 앞의 ‘실습 목적 및 내용:’이라는 표시는 삭제합니다.

## 2. 파일 위치와 작성 범위

- 실습 문서는 `edu-ai-agent/docs/`에 저장합니다.
- 현재 문서처럼 기존 노트북 이름의 주제와 번호를 유지하고 확장자를 `.md`로 바꿉니다.
- 예: `02-llm-api-and-message-roles.ipynb`에 대응하는 문서는 `docs/02-llm-api-and-message-roles.md`입니다.
- 파일명의 `02`는 교육 구성상의 식별자이고, 본문의 `1.`, `1.1`은 문서 내부 학습 순서입니다. 서로 같은 번호일 필요는 없습니다.
- 노트북 목록은 구성안입니다. 목록에 있다는 이유만으로 나머지 39개 문서나 `.ipynb` 파일을 일괄 생성하지 않습니다.
- 후속 문서의 일차별 하위 폴더가 별도로 요청되면 그 위치를 따릅니다. 현재는 `docs/` 아래의 일차별 폴더 구조까지 확정된 것은 아닙니다.
- 요구사항·범위가 불명확하면 확인하고, 교육 내용이나 버전 번호를 임의로 추가하지 않습니다.

## 3. 문서 전체 구조

문서 제목은 H1으로 한 번 표시합니다. 실습 시작 전에는 학습 목표·범위와 실행 환경·준비사항을 설명합니다. 이 도입부는 현재 적용 사례처럼 번호 없는 H2로 둘 수 있습니다.

셀 1에 해당하는 실습부터는 다음 계층을 사용합니다.

| 요소 | Markdown 형식 | 예시 |
| --- | --- | --- |
| 문서 제목 | H1 | `# LLM API와 메시지 역할 실습` |
| 도입부 | 번호 없는 H2 | `## 학습 목표와 범위` |
| 주제별 실습 섹션 | 번호 있는 H2 | `## 1. 실습 환경 설정` |
| 개별 실행 셀 제목 | 번호 있는 H3 | `### 1.1 실습 패키지 설치` |
| 실습 후 확인 | 번호 있는 H2 | `## 8. 학습 확인과 제공자 비교` |
| 참고 자료 | 번호 있는 H2 | `## 9. 참고 문서` |

- 섹션 번호 `N`은 문서 안에서 순서대로 증가시킵니다.
- 하위 번호는 각 섹션에서 `N.1`부터 다시 시작합니다.
- 관련된 셀을 같은 섹션에 묶습니다. 셀 하나마다 별도 상위 섹션을 만들 필요는 없습니다.
- ‘셀 1’, ‘셀 2’처럼 전체 셀 번호를 제목으로 사용하는 형식은 현재의 번호 체계로 대체합니다.
- 본문에서 다른 실습을 가리킬 때도 ‘셀 7’ 대신 ‘3.1절’처럼 현재 번호를 사용합니다.
- 오류 메시지나 코드 주석에 이전 셀 번호가 남아 있다면 함께 수정합니다.
- 셀 개수는 주제에 맞게 정합니다. 현재 예제의 15개 셀을 모든 문서에 강제하지 않습니다.

## 4. 개별 실습 셀 작성 형식

각 하위 섹션은 다음 순서를 따릅니다.

1. `N.N` 형식의 실습 제목
2. 목적과 내용을 설명하는 불릿
3. 노트북 Code 셀에 복사할 Python 코드 블록
4. `**결과:**`
5. 출력·해석·확인 사항을 설명하는 불릿

### 4.1 코드 앞의 목적과 내용

- ‘실습 목적 및 내용:’이라는 표시나 별도 소제목을 넣지 않습니다.
- 실습 제목 다음에 바로 불릿을 작성합니다.
- 무엇을 배우는지, 코드가 어떤 작업을 하는지 구체적으로 설명합니다.
- 서로 다른 목적이나 작업은 별도 불릿으로 나눕니다.
- 필요한 경우 선행 실습, 입력할 값, API 호출 횟수를 설명합니다.
- 코드의 모든 줄을 그대로 풀어 쓰기보다 실습 이해에 필요한 내용을 설명합니다.

### 4.2 Python 코드 블록

- 코드 블록의 언어는 `python`으로 표시합니다.
- 각 블록은 Jupyter Notebook에서 하나의 Code 셀로 실행할 단위로 작성합니다.
- 문서의 위에서 아래로 실행하면 필요한 import·함수·변수가 순서대로 준비되도록 구성합니다.
- 하나의 셀로 복사할 수 있다는 것은 앞선 셀에 대한 의존성이 없다는 뜻은 아닙니다. 의존성이 있으면 설명합니다.
- 실행 결과나 설명 문장을 Python 코드에 섞지 않습니다.
- 학습자가 수정해야 할 설정과 입력값을 명확히 표시합니다.
- API 키는 코드에 직접 기입하지 않고 환경 변수나 숨김 입력 등으로 받습니다.

### 4.3 코드 뒤의 결과

- 표시 이름은 `**결과:**`로 통일합니다.
- ‘결과 설명:’이라는 이전 표현은 사용하지 않습니다.
- 결과 내용은 코드 블록 다음에 불릿으로 작성합니다.
- 예상 출력, 출력의 의미, 성공 여부를 확인하는 방법을 구분합니다.
- 모델 답변이 달라질 수 있으면 고정된 문장을 정답처럼 제시하지 않고 관찰할 기준을 설명합니다.
- 오류나 빈 응답이 발생했을 때 확인할 항목이 필요하면 함께 안내합니다.
- 실제 실행하지 않은 결과를 관측한 사실처럼 기재하지 않습니다.

### 4.4 복사해서 사용하는 형식 예시

아래는 문서 작성 형식을 보여주는 템플릿입니다. 바깥쪽 코드 블록을 제외한 내용을 실제 문서에 적용합니다.

````markdown
## 1. 실습 환경 설정

### 1.1 Python 실행 환경 확인

- 현재 노트북 커널이 사용하는 Python의 버전을 확인합니다.
- 패키지를 설치할 때 사용할 Python 실행 경로를 확인합니다.

```python
import sys

print("Python 버전:", sys.version.split()[0])
print("Python 실행 경로:", sys.executable)
```

**결과:**

- Python 버전과 실행 파일의 경로가 출력됩니다.
- 실행 경로를 통해 현재 노트북 커널이 어떤 Python 환경을 사용하는지 확인합니다.
- 학습자가 선택한 가상환경과 다르면 노트북의 커널 설정을 확인합니다.
````

## 5. 현재 실습의 환경 선택과 후속 문서 적용

현재 `02-llm-api-and-message-roles.md`는 앞선 비교 요청을 반영해 Ollama를 기본값으로 두고 OpenAI API를 선택할 수 있도록 작성했습니다.

- 두 환경에서 공통으로 배우는 API 요청·응답과 메시지 역할을 중심으로 구성합니다.
- 서버 주소, 모델 이름, 인증 방법 등 환경별 차이는 설정 단계에서 구분합니다.
- 로컬 Ollama는 노트북 커널이 실행되는 위치를 확인하도록 안내합니다.
- OpenAI 모드에서는 모델 호출과 반복 실행에 사용량이 발생한다는 점을 설명합니다.
- API나 모델의 호환 기능을 확인하고 모든 제공자의 기능이 같다고 단정하지 않습니다.
- 임베딩, 도구 호출, 구조화 출력 등 후속 주제는 해당 모델의 지원 여부를 별도로 확인합니다.
- Claude Code·Codex 구독 활용은 API 대체 여부를 논의한 비교 주제입니다. 별도 요청 없이 이 실습의 실행 경로로 추가하지 않습니다.
- 모든 후속 문서에 두 제공자 지원을 일률적으로 강제하지 않습니다. 주제와 사용자 요청에 맞춰 범위를 정합니다.
- Gemini는 원래 과정에 명시되어 있지만 현재 예제의 구현 대상에는 포함되지 않았습니다. 후속 작성 시 범위에서 빠진 제공자를 이미 구현한 것처럼 표시하지 않습니다.

라이브러리와 API의 기능·사용법을 새로 작성하거나 변경할 때는 해당 공식 문서를 확인하고, 관련 설명 근처 또는 참고 문서에 출처를 연결합니다.

## 6. 기존 문서 수정 요령

- 먼저 대상 문서의 현재 내용과 제목 체계를 읽습니다.
- 사용자 요청에 해당하는 설명과 형식만 수정하고 관련 없는 내용을 임의로 확장하지 않습니다.
- 불릿이나 제목 변경 요청에서는 코드의 실행 로직을 유지합니다.
- 제목 번호가 바뀌면 본문 참조와 코드 안의 안내 메시지도 확인합니다.
- 설명을 불릿으로 나눌 때 조건, 예외, 주의사항, 출처가 누락되지 않도록 합니다.
- 이미 적용한 ‘목적 표시 삭제’, ‘결과:’, 번호 체계를 후속 수정에서 되돌리지 않습니다.
- 코드 변경이 필요한 오류를 발견하면 형식 변경과 구분하여 조치 내용을 알립니다.
- 문서 수정만 요청받은 경우, 실제 모델 호출이나 패키지 설치를 자동으로 실행할 필요는 없습니다.
